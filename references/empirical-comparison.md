# 實證對比 #2（2026-08-12）— 複雜 Agent 場景（**極端構造案例**）

> ⚠️ 本案例為**刻意構造的極端場景**（大 CSV 全量重送），非典型工作量；真實 Agent 場景降幅請參考典型預期 30–50%。

題目：分析 Q2 銷售數據、找下滑前 3 產品線+建議（多輪 + 工具回傳 213 行 CSV）｜分詞器：cl100k_base

| 項目 | 不用技能 | 用技能 | 降幅 |
|------|---------|--------|------|
| 輸入 token | 5989 | 237 | 96.0% |
| 輸出 token | 612 | 258 | 57.8% |
| 總 token | 6601 | 495 | 92.5% |
| 總成本 | $0.02715 | $0.00424 | 84.4% |

關鍵發現：
- 降幅主因 = 工具回傳過濾（原始 CSV 5508 token → 聚合精華 101 token），佔 A 版輸入 92%。
- 任務越複雜，攻輸入端的優勢越大：單輪 #1 總降 68.8% → 多輪+工具 #2 總降 92.5%。
- 印證技能第五段「工具回傳先過濾」是 Agent 場景最大槓桿。

複現：`scripts/repro.py` 可重現同類對比；本方法論亦適用於任何真實 LLM 端點（腳本結構見 #3）。

# 實證對比 #3（2026-08-12）— 真實 LLM 調用（本地 Ollama qwen3:8b）

題目：同 #2（Q2 銷售分析 + 213 行 CSV 工具回傳）｜但為**真實調用**，非 tiktoken 模擬
方法：打本地 Ollama /api/chat，取模型自身回傳的 prompt_eval_count（輸入）與 eval_count（輸出）

| 項目 | 不用技能 | 用技能 | 降幅 |
|------|---------|--------|------|
| 輸入 token | 2050 | 184 | 91.0% |
| 輸出 token | 700* | 330 | 52.9% |
| 總 token | 2750 | 514 | 81.3% |
| 耗時(s) | 24.6 | 11.5 | 53.0% |

\* A 版輸出撞 num_predict=700 上限被截斷（無技能版易冗長，截斷仍未答完）；B 版 330 自然收斂。

診斷：Ollama 多輪 prompt_eval_count 不計入 assistant 長內容（CSV 放 assistant 僅 20 token，單輪 user 含同段 2050），故改用「壓平單輪」構造拿真實輸入對比。

tradeoff 證據：A 版模型讀原始 CSV 後答「鏡頭膜/快充線/手機殼-黑」；B 版只給聚合精華卻答不同前 3 名——「過濾工具回傳」確實省 token，但可能損失細節，是**真實 tradeoff 而非零成本**。
**避免方法**：聚合保留 Top-N + 異常標記（`scripts/aggregate_tool_output.py`，IQR 法），勿一刀砍光；任務需逐行細節（如除錯）時**不聚合**，改走別的成本槓桿（caching/路由）。

結論：與 #2 方向一致（輸入 -91% vs -96%、總 -81% vs -92%），證實 token saver 策略在真實 LLM 上有效；輸入端降幅最顯著。

複現：真實調用方式見 `scripts/repro.py` 說明；本檔數據為實測記錄，不依賴任何外部檔案。

# 實證對比 #4（2026-08-12）— 真實雲端 LLM（Deepseek-V4-Flash，WorkBuddy 閘道）

題目：如何讓 Agent 切換任務時保持同一 Agent、不失憶、保持記憶完整性與上下文延續性
方法：**真實驗證**——同一題目、同一個模型（Deepseek-V4-Flash）分兩次作答；用量取 WorkBuddy 介面「已消耗 ◇」計數器增量
- A（不套技能）：3014 字長篇散文（開場鋪陳+反覆申論+無結構）
- B（套 token saver）：613 字結構化列點（等價資訊：五層架構+實例+核心結論）

| 項目 | A 不套技能 | B 套技能 | 降幅 |
|------|:---:|:---:|:---:|
| 介面計數增量（◇） | 0.97 | 0.63 | **35.1%** |
| 輸出 tiktoken 估算 | 3938 | 619 | 84.3% |
| 輸入（題目） | ~69 | ~69 | 0% |

解讀（重要，避免誤讀）：
- 介面計數含**固定輸入開銷**（system prompt + 對話歷史 + 題目），兩版相同，故增量只反映輸出差，被攤薄 → 可見降幅 35.1% 是「含固定成本」的下限。
- 純輸出 tiktoken 估算 84.3% 是「不含固定成本」的上限。
- 真實值介於兩者之間，**典型約 50%**；任務愈深（輸入佔比愈小）愈接近 84%。
- ◇ 單位非原始 token，為平台加權單位；比率（-35.1%）跨模型可比。

結論：**在真實外部雲端模型上，套技能省 token 已被實測證實（介面計數 -35.1%，下限）；純輸出端減幅更大（-84.3%，上限）**。此為第一個「真雲端 + 真計費」證據，補齊 #1–#3 的模擬/本地缺口。

複現：`scripts/repro.py`；或任何平台自訂指令貼常駐片段後以同任務實測（見 always-on-guide）。

# 實證對比 #5（2026-08-12）— 真實雲端**完整 Agent 迴圈**（Deepseek-V4-Flash）

題目：分析 2026 上半年銷售與缺陷數據，找出下滑最嚴重的產品線並給 3 條建議
方法：**真實驗證全迴圈**——真實工具呼叫（2 個工具回傳）+ 3 輪推理，同模型 Deepseek-V4-Flash，用量取介面計數器增量
- A（不套技能）：工具回傳 150 行銷售 + 120 行缺陷**原始數據全進上下文**；最終長篇散文報告
- B（套 token saver）：工具回傳**先聚合**（150 行→7 行、120 行→8 行）才入上下文；最終結構化 ≤300 字

| 項目 | A 不套技能 | B 套技能 | 降幅 |
|------|:---:|:---:|:---:|
| 全迴圈計數增量（◇） | 0.95 | 0.45 | **52.6%** |
| 工具回傳進入上下文的行數 | 270 行原始 | 15 行聚合 | 94.4% |

關鍵發現：
- **完整迴圈降幅（52.6%）> 單次作答（#4 的 35.1%）**——原始工具回傳在每一輪都重新進入上下文（R2 含 R1 數據、R3 含全部），浪費呈複利式累積；B 每輪壓縮，差距逐輪拉大。
- B 版**在同一對話**執行（輸入含 A 版整段歷史，對 B 不利）仍省 52.6% → 乾淨環境下真實降幅只會更高。
- 印證「工具回傳先過濾/聚合」是 Agent 迴圈最大槓桿：270 行 → 15 行，單項省 94%。
- 兩版結論一致（鏡頭膜 -73.9% 最嚴重、品質反噬、3 條建議同向）→ 資訊損失小。

結論：**真實雲端完整 Agent 迴圈，套技能省 52.6%（介面計數）**，且隨迴圈輪數增加而放大。此為目前最接近生產實況的證據。

複現：`scripts/repro.py`；實測數據為計數器實錄，詳見 always-on-guide 實證支撐段。
